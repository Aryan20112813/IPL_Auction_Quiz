# File Structure — Quiz for IPL Auction

Recommended project layout for the stack chosen in [`PRD.md`](./PRD.md) §12: **Next.js (App Router, TypeScript) monolith + PostgreSQL (Prisma) + Tailwind CSS + Zod, using polling for updates.** One repository, one deployable app, one database.

Design rules behind the layout:
- **Route handlers stay thin** (parse → authenticate → call a service → shape the response).
- **All business rules live in `src/server/`** (quiz logic, ranking, finalisation) so they can be unit-tested without HTTP.
- **Validation schemas are shared** (`src/lib/validation/`) by client forms and API routes.
- **Nothing that contains the answer key is ever placed under `public/`** or imported by client code.
- **Names match the documents:** states `CREATED | WAITING | ACTIVE | ENDED | EXPIRED`, statuses `IN_PROGRESS | SUBMITTED | AUTO_SUBMITTED`, tables `questions`, `quizzes`, `quiz_questions`, `participants`, `answers`, `results`.

## 2. What each area is for

### 2.1 Documentation

| Path | Why it exists | Contains | Used by |
|---|---|---|---|
| `docs/PRD.md` | Single source of product requirements and acceptance criteria | Features, rules, ranking, API, DB, security, MVP scope | Whole team; QA derives tests from §17 |
| `docs/Workflow.md` | Explains how the system behaves step by step | Host/participant flows, state machines, timer, finalisation, diagrams | Developers implementing services and hooks |
| `docs/FILE_STRUCTURE.md` | Maps design to code locations | This file | Developers onboarding |
| `docs/DEPLOYMENT.md` | Operational guide | Hosting steps, env variables, rehearsal and event-day checklist | Whoever deploys and runs the event |
| `README.md` | First thing contributors read | Quick start, scripts, doc links | Everyone |

### 2.2 Question bank

| Path | Why | Contains | Used by |
|---|---|---|---|
| `data/questions/IPL_Quiz_Questions.md` | Human-friendly, reviewable list of the 100 questions | `## Q<n>.` blocks with options A–D, `**Answer:**`, `**Difficulty:**` and a summary table | Content editors; `parse-questions.ts` |
| `data/questions/questions.json` | Machine-readable generated copy | `[{ id: "Q001", text, options: {A,B,C,D}, correctOption, difficulty }]` | `prisma/seed.ts`, tests |
| `scripts/parse-questions.ts` | Keeps the markdown the single editable source | Parser for the documented format; assigns ids `Q001…Q100` | `npm run questions:parse` |
| `scripts/validate-questions.ts` | Guards the bank's integrity | Asserts 100 questions, unique text, 4 distinct options, valid answer, valid difficulty, ≥ 25 active | CI and pre-seed step |
| `prisma/seed.ts` | Loads the bank into the database | Upsert by `id` (safe to re-run) | `npm run db:seed` |

> The question files contain the **answer key**. They are intentionally **outside `public/`** and are only read by seed/validation scripts. The running API reads answers from the database, server-side, for scoring only.

### 2.3 Database

| Path | Why | Contains | Used by |
|---|---|---|---|
| `prisma/schema.prisma` | Declares models and relations | `Question`, `Quiz`, `QuizQuestion`, `Participant`, `Answer`, `Result`; enums for state/status; unique constraints (`code`, `(quizId, normalizedName)`, `(quizId, questionId)`), indexes | Prisma client generation, migrations |
| `prisma/migrations/` | Reproducible schema | Generated SQL plus hand-added `CHECK` constraints (`position BETWEEN 1 AND 25`, option ∈ A–D, state values) and the leaderboard index | Deployment (`prisma migrate deploy`) |
| `src/server/db/prisma.ts` | One shared client | Singleton configured for pooled/serverless connections | All services |
| `src/server/db/transactions.ts` | Central place for locking patterns | `withTransaction`, `FOR SHARE`, `FOR UPDATE`, `NOWAIT` helpers | `answer.service`, `quiz.service`, `finalize` |

### 2.5 API / server logic

| Path | Why | Contains | Used by |
|---|---|---|---|
| `src/app/api/v1/**/route.ts` | One file per endpoint in `PRD.md` §14 | Thin handler: `wrap(schema, auth, service)` | Browser via `api-client.ts` |
| `src/server/http/handler.ts` | Consistent behaviour | Zod parsing, error mapping to `{error:{code,message},serverTime}`, `serverTime` injection, logging | Every route |
| `src/server/http/errors.ts` | Central error vocabulary | Codes from PRD §14 | Services and handler |
| `src/server/http/rate-limit.ts` | Basic abuse prevention | Per-IP/route limits (generous for join/save, strict for `rejoin` and create) | `middleware.ts`, selected routes |
| `src/server/services/*.service.ts` | Use cases | Orchestrate auth result, validation output, DB calls and logic modules | Route handlers |
| `src/server/dto/*` | Prevent leaks | Explicit field whitelists | Services when returning data |

### 2.6 Quiz logic

| Path | Why | Contains | Used by |
|---|---|---|---|
| `src/server/quiz/select-questions.ts` | Fair random selection | Partial Fisher–Yates over active ids using `crypto.randomInt` | `quiz.service.create` |
| `src/server/quiz/room-code.ts` | Unique unambiguous codes | 6 chars from `ABCDEFGHJKMNPQRSTUVWXYZ23456789` with retry | `quiz.service.create` |
| `src/server/quiz/state.ts` | One definition of state rules | `effectiveState`, guards that map state → allowed action → error code | All services |
| `src/server/quiz/timer.ts` | Server-authoritative time | `ends_at` computation and expiry checks based on DB time | start, answers, submit, status |
| `src/server/quiz/finalize.ts` | The single closing routine | Lock, auto-submit, recompute scores, rank, mark final; idempotent; used by End Quiz and lazy expiry | `quiz.service.end`, `GET /quizzes/{code}`, answer/submit paths |

### 2.7 Ranking logic

| Path | Why | Contains | Used by |
|---|---|---|---|
| `src/server/ranking/score.ts` | Single scoring definition | Set-based SQL and a pure `scoreAnswers()` for tests (1 point per correct) | `answer.service.submit`, `finalize` |
| `src/server/ranking/time-taken.ts` | Fair tie-break clock | `effective_start = max(joined_at, started_at)`; auto-submit rule | `score.ts`, `finalize` |
| `src/server/ranking/rank.ts` | Ordering and rank | `RANK() OVER (score DESC, time_taken_ms ASC)`; provisional vs final readers | `leaderboard.service`, `quiz.service.getHostDashboard`, `finalize` |

### 2.8 Authentication / host authorisation

| Path | Why | Contains | Used by |
|---|---|---|---|
| `src/server/auth/tokens.ts` | Token generation and hashing | 32-byte random tokens, SHA-256 with server-side pepper | create, join, rejoin |
| `src/server/auth/require-host.ts` | Protects host-only endpoints | Reads `Authorization: Bearer`, hashes, `timingSafeEqual` against the quiz's `host_token_hash` | start, end, dashboard, leaderboard (host mode) |
| `src/server/auth/require-participant.ts` | Binds a participant to one quiz | Looks up token hash, ensures `participant.quizId` equals the quiz in the URL | questions, answers, submit, me, leaderboard |
| `src/hooks/useSession.ts` | Client-side persistence | `localStorage` keys `ipl-quiz:host:{code}` and `ipl-quiz:{code}:participant`; parses `#t=` host link | All pages |

### 2.9 Validation

| Path | Why | Contains | Used by |
|---|---|---|---|
| `src/lib/validation/room-code.ts` | Consistent code handling | Alphabet regex, normaliser | Join form, all `[code]` routes |
| `src/lib/validation/participant.ts` | Name rules and uniqueness key | 2–30 chars, allowed charset, `normalizeName()` (NFKC, lower-case, collapse spaces) | Join form, `participant.service` |
| `src/lib/validation/answers.ts` | Safe answer payloads | `{position 1..25, option A|B|C|D|null}[]` max 25, unique positions | `PUT /answers`, `POST /submit`, client queue |
| `src/lib/validation/pagination.ts` | Bounded queries | `limit` 1–100, `offset` ≥ 0 | Dashboard, leaderboard |

### 2.10 Real-time communication (polling)

| Path | Why | Contains | Used by |
|---|---|---|---|
| `src/lib/config.ts` | One place for intervals | `POLL_LOBBY_MS = 8000 (±2000 jitter)`, `POLL_ACTIVE_MS = 30000`, `POLL_SUBMITTED_MS = 15000`, `POLL_HOST_MS = 5000`, `HIDDEN_TAB_MULTIPLIER = 3` | Hooks |
| `src/hooks/useQuizStatus.ts` | Adaptive polling | Interval selection by screen, jitter, Page Visibility handling, immediate poll at countdown 0:00 | `/join`, `/play/[code]` |
| `src/hooks/useServerClock.ts` | Cosmetic timer synced to server | Offset from `serverTime`, per-second remaining time | `TimerDisplay` |
| `src/hooks/useHostDashboard.ts` | Host refresh | 5 s polling with pagination | `/host/[code]` |
| `src/hooks/useAnswerSync.ts` | Prevents answer loss | Debounced saves, `localStorage` queue, exponential backoff, flush on `online` and at 0:00 | `QuestionCard` |

No WebSocket/SSE directory exists on purpose. If events later outgrow polling, add `src/app/api/v1/quizzes/[code]/events/route.ts` (SSE) and keep the polling hooks as the fallback.
